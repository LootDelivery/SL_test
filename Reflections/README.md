# SLRR Glass Reflection Runtime Control

Набор для управления силой отражений на стёклах **в рантайме, слайдером** —
как тонировка, но для ReflectionIntensity материалов стекла. Без патча .exe
на диске и без правки .scx-файлов.

## Версия 1.12 (текущая) — фикс краша на загрузке/сохранении + живое обновление через пересборку рендер-чилда

### Почему v1.11 крашилась на загрузке машины / сохранении (и почему голый кузов не крашился)

Лог двух сессий показал: в обеих краш происходит **сразу после строки
`MAGIC ... 0x7AFD...` (band 2, рендер-тип)** — ни `scan ok`, ни
`no refl entries`, ни `E2a/E2b/E2c` после неё. Band 1 (0x7AFE, меш)
отрабатывал чисто. Голый кузов не крашился, потому что без стёкол тюнер
вообще не шлёт magic.

Разбор exe по дизассемблеру полностью опроверг посылку v1.11:

1. **`GetData` рендер-типа возвращает `ресурс+0x80`** (`lea eax,[ecx+0x80];
   ret` @ 0x54A820) — встроенный под-объект, а класс рендер-типа —
   `new(0x140)`, vt 0x5F3A68 (проверено по switch фабрики ресурсов
   0x536A2B, case тип-14). Этот под-объект — **не меш-объект**: поля
   `+0x48/+0x4C` там — не «массив записей материалов / счётчик».
2. **Список `+0x44/+0x48/+0x50`, который v1.11 принимала за список живых
   обёрток материалов, принадлежит классу СЦЕНЫ** (vt 0x5F38A8): импортёр
   0x5461A0 линкует туда узлы чанков по таблице фабрик 0x60C84C — это
   'camera'/'car'/'part'/'trigger'... — объекты сцены, 0x18/0x1C байт,
   а не GfxMaterial-обёртки 0x2C. Фабрика 0x4E1725 вообще не вызывается
   из этого импортёра.
3. Оба обхода v1.11 имели **незащищённые разыменования**:
   `gr_walk_root` читал `records[i] = [edi+idx*4]` без проверки `edi`
   (значение `[тип_подобъект+0x48]` — мусор), а `gr_walk_list` на
   `.wl_next` читал `node->prev` у **невалидированного** узла (туда
   прыгает проваленная проверка VirtualQuery). Любое из двух мест —
   access violation. Отсюда стабильный краш на любой загрузке/сохранении
   машины со стёклами.

### Что сделано в v1.12

1. **Оба обхода закрыты guard'ами**: `gr_walk_root` валидирует весь
   диапазон массива записей (`gr_readable(vecs, count*4)`) до первого
   чтения; `gr_walk_list` валидирует узел до чтения `prev`; кандидат-
   скан валидирует окно `gr_data[0..0x200)`; `gr_dump_all` больше не
   пишет в файл диапазон, не проверив его читаемость (GRD1), и
   валидирует массив записей (GRM1). Класс краша устранён целиком.
2. **Band 2 (0x7AFDxxxx) переведён в dump-only**: ничего не сканирует,
   ничего не пишет. Вместо этого `gr_dump_chain` снимает (каждый
   диапазон проверен VirtualQuery) цепочку рендер-типа: бокс референса
   (GRT0, 0x40), сам ресурс типа (GRT1, 0x140), его под-объект +0x80
   (GRT2, 0x100) и объект-контент `[подобъект+0x18]` (GRT3, 0x200) —
   в `grefl_dump.bin`, секциями с заголовками GRT0..GRT3. В логе —
   строка `band2 type chain recv/res/sub/content: ...`.
3. **Живое обновление переехало на Java-сторону** — `refreshRenderChild()`:
   рендер-чилд перечитывает материалы только при (пере)создании, а
   `setRenderType`/`setMesh` с тем же id — no-op (`Part_rebind*Res`
   выходят по `cmp id, id`). Поэтому тюнер делает **отскок рендер-типа
   A→B→A внутри одного хендлера**: промежуточный чилд создаётся и
   умирает до следующего кадра (никогда не рисуется — без мерцания),
   а финальный пересоздаётся из только что пропатченных меш-копий.
   Случаи: активен оверлей прозрачности → private→original→private +
   перекраска инстанса; сток → original→private→original (или через
   временный duplicate paint-can типа, если оверлея нет вовсе).
4. `applyReflection()` (патч меша) и `applyReflectionLive()` (патч +
   пересборка) разведены: слайдер, конец сессии тюнинга и onInstalled —
   Live; инвентарная превью, открытие меню, applyAppearance — патч-only
   (там пересборка не нужна/вредна).
5. Отправка `0x7AFDxxxx` из Java удалена (как и поля
   `reflCurTypeHandle`/`reflOrigTypeHandle`); протокол снова
   однополосный: `0x7AFExxxx` на меш + обычный `setRenderType` откат.

### Ожидаемое поведение

- Краш на загрузке/сохранении машины со стёклами — исчез (band 2 больше
  не ходит по памяти; все обходы под VirtualQuery-защитой).
- Слайдер Reflection меняет картинку **сразу** (пересборка рендер-чилда
  в том же кадре), значение по-прежнему живёт в ресурсе меша и
  переживает реимпорты (SAVE, выезд/въезд в гараж).
- Прозрачность/тонировка не ломаются: их цвет после отскока
  восстанавливается через `applyInstanceColor` (тот же
  `setColor(ARGB)`, что использует слайдер прозрачности).
- Прочие альфа-объекты не затрагиваются вообще (никаких apply-вызовов
  и глобального D3D-состояния со стороны DLL с v1.11).

## Версия 1.11 — живой патч рендер-ТИПА + откат опасного apply (откат в v1.12)

### Почему v1.10 портил альфу другим объектам и не двигал стекло

Два симптома v1.10 объясняются одной и той же архитектурой, доказанной
по дизассемблеру exe:

1. **Материалы, которые реально читает рендер, живут НЕ в меше.**
   Импортёр материалов (`0x5461A0`, вызывается методом рендер-типа
   `0x546C10`) создаёт для каждого материала **свежую** обёртку 0x2C
   и **свежий** массив стадий 0xD8 (фабрика `0x4E1725`: `new(0x2C)` +
   `new(0xD8)`) и линкует их в связный список **на объекте рендер-ТИПА**
   (+0x44 head / +0x48 tail / +0x50 count; запись = узел−4,
   запись+0 = обёртка). Обёртки в меше — лишь шаблоны времени парсинга.
   Поэтому v1.9/v1.10 писали в шаблоны: после SAVE (пересборка сцены →
   реимпорт из меша) значение проявлялось, а в рантайме — нет.
2. **apply — не рендер-функция.** Стоковый apply (vt+0x04, для стекла
   0x4C4330) пушит глобальное состояние устройства: SetRenderState
   (0x3C = TFACTOR), SetTextureStageState(0, ALPHAOP, SELECTARG2) и
   перезапись глобалов света (0x4E7380). Дергая его из слайдера, v1.10
   затирал состояние, на которое рассчитывали ДРУГИЕ альфа-объекты —
   отсюда «альфа теряется, пока двигаю ползунок». А стекло всё равно не
   менялось: его состояние берётся из обёрток ТИПА, которые мы не трогали.

### Что сделано в v1.11

1. **Вызов apply полностью удалён.** Порча альфы других объектов
   исчезает — мы больше не трогаем глобальное D3D-состояние вовсе.
2. **Вторая magic-полоса `0x7AFD0000`** (значение = 31485*65536 +
   percent): тюнер шлёт её на `RenderRef` **рендер-типа** детали.
   DLL обходит связный список материалов типа (новый `gr_walk_list`:
   хвост → prev, ограничен счётчиком с потолком 16, каждый адрес
   проверен VirtualQuery) и пишет те же слоты ReflectionIntensity
   (+4..+0x18 и сырую копию) в ЖИВЫЕ обёртки, которые читает рендер.
3. Полоса `0x7AFE0000` (меш) сохранена — она делает значение стойким к
   реимпортам (то, что раньше «применял» SAVE).
4. Если активен оверлей прозрачности (деталь на приватном paint-can
   типе), тюнер дополнительно патчит и исходный тип — чтобы при снятии
   оверлея выбранная сила уже была на месте.
5. Диагностика: если на типе слотов не найдено — в логе будет
   `no refl entries` + автодамп `grefl_dump.bin` (секция GRD1 снимает
   0x2000 байт объекта типа — этого достаточно, чтобы точно
   доразобрать структуру за одну итерацию).

## Версия 1.10 — live apply (откат в v1.11)

### Почему v1.9 писал 14 правильных адресов, а стёкла не менялись

Лог v1.9 оказался золотым: `MAGIC` доходит (1530 вызовов за сессию,
слайдер 100→20), `scan ok root/slots/mats/data: ... 0x0000000E 0x00000002 ...`
— обход находит 2 материала стекла и 14 слотов ReflectionIntensity,
запись проходит, кэш работает, крашей нет. Значение **действительно
легло в память** — но движок перечитывает эти слоты только когда
рендер-объект (пере)создаётся, т.е. при парсинге SCX (call sites
0x5463BB / 0x5465DA). Именно поэтому кнопка SAVE «применяла» отражение:
пересохранение пересоздаёт объект и apply запускался сам.

### Что сделано в v1.10

1. После цикла записи DLL вызывает **стоковый apply-виртуал каждого
   материала** (vt+0x04; для glass-класса 0x33 это 0x4C4330, аргумент 0).
   apply перечитывает entries+0x28 (только что записанное значение),
   пересобирает light-цвета (0x4E7380, идемпотентно) и пушит значение
   в живое D3D-состояние: SetRenderState(0x3C, ARGB) + одна stage-операция.
2. Обход сканирования теперь запоминает wrapper-объекты материалов
   (до 8 на кэш-слот) — именно их gr_apply_all и применяет.
3. Новая строка лога `apply ok cnt/raw/data/recv` (первые 3 применения)
   подтверждает, что apply реально вызвался и сколько раз.
4. Безопасность: apply вызывается в контексте скрипт-натива на главном
   потоке — ровно там же, откуда его вызывает сам движок; регистры
   ebx/esi/edi экранированы (урок v1.6), wrapper проверен VirtualQuery,
   vtable и apply-указатель проверены на null.

## Версия 1.9 — найдена и устранена ПРИЧИНА молчания magic

### Причина, по которой v1.5–v1.8 не работали (доказана по дизассемблеру)

Лог v1.8 дал ключевую улику: в поле `val` **всегда** стояло `0x00000003`.
Разбор интерпретатора TUFA (`invokeMethod @ 0x41FBC0`, таблицы диспатча
`0x420788`/`0x42079c`) и `JVM_UnboxArg @ 0x45D910` показал:

1. Интерпретатор вызывает натив-метод с **одним** стековым аргументом —
   адресом ячейки ресивера (`&this_cell`) — а в **ECX кладёт не аргумент,
   а индекс варианта типа возврата** из таблицы диспатча. Для void-методов
   (`set(I)V`) это всегда **3**. Поэтому все fwd-строки v1.8 показывали 3 —
   это был код типа «V», а не значение.
2. Само значение int-аргумента натив получает так: стоковый натив начинает
   с `push ecx` (плейсхолдер!) и вызывает
   `JVM_UnboxArg(this_cell, &&this_cell, &плейсхолдер)`, который берёт
   реальные аргументы из value-массива интерпретатора (`this_cell+8`) по
   зарегистрированному дескриптору (`this_cell+0xC`) и **перезаписывает
   плейсхолдер**. Только после этого `[esp]` — настоящее значение.
3. v1.5–v1.8 проверяли magic **в ECX до анбоксинга** → всегда видели 3 →
   magic никогда не совпадал → все вызовы уходили в стоковый натив.
   Побочно: magic-вызовы тюнера молча перепривязывали `targetMeshHandle`
   к «ресурсу» 0x7AFExxxx (v1.9 это тоже убирает — magic больше не доходит
   до SetRes).

### Что сделано в v1.9

1. **Хук сначала исполняет стоковый пролог натива 0x47CF80 байт-в-байт**
   (`push ecx` → `JVM_UnboxArg` → lookup ресивера), и только потом
   проверяет magic по **настоящему** значению в `[esp]`.
2. Чужие вызовы завершают стоковую последовательность **инлайн**
   (`ResHandle::Set(value)` → pop → ret) — поведение идентично оригиналу.
3. Свои (magic) вызовы идут в v1.4-обход материалов с уже готовым
   ресивером от стокового lookup — собственный marshal больше не нужен.
4. **Лог теперь показывает реальные значения**: fwd-трасса (первые 100 +
   каждая 256-я) пишет истинные аргументы set(), а не «3».
5. **Детектор SMALL**: каждое уникальное значение < 0x10000 пишется в лог
   (до 40). Если компилятор игры сложит `31486 * 65536` неправильно (напр.
   в 0), тюнер будет слать голые проценты 0..100 — мы это увидим сразу.
6. NEAR-MISS (искажённый magic, диапазоны 0x7AFC0000–0x7B000000 и
   0x7AF0–0x7B10) — оставлен, теперь тоже проверяет реальное значение.

### Как читать лог v1.11

| Что в логе | Диагноз |
|-----------------------------------------------|---------|
| `MAGIC ... 0x7AFE....` + `scan ok ...` | меш-полоса: значение записано в шаблоны (стойкость к реимпортам) |
| `MAGIC ... 0x7AFD....` + `scan ok ...` | полоса ТИПА: значение записано в живые обёртки — отражение должно меняться сразу |
| `MAGIC ... 0x7AFD....` + `no refl entries` | до типа дошли, но список материалов не похож на ожидаемый — пришлите лог + `grefl_dump.bin` (это заготовка под v1.12) |
| `MAGIC ... 0x7AFD....` + `E1` | magic дошёл, но ресивер типа не разрезолвился (нужен лог) |
| `MAGIC ... 0x7AFD....` + `E2a/E2b/E2c` | обрыв на этапе ресурса (точное место в строке); E2b на типе = неподходящие lock-флаги — пришлите лог |
| `NEAR-MISS ...` | magic доходит, но ИСКАЖЁН — значение в строке покажет, как именно |
| `SMALL ...` со значением 0..100 при движении ползунка | компилятор игры испортил `31485*65536`/`31486*65536` (скорее всего в 0) — адаптирую протокол за одну итерацию |
| только `fwd ...` и ничего при движении ползунка | set() от тюнера не вызывается вовсе → проверяем, какой .class реально загружен в игре |
| `fwd ...` с обычными значениями | стоковый трафик (конструкторы `new ResourceRef(id)`) — так и должно быть |

Четвёртое поле (`ret`) = адрес возврата: `0x004200B9` = интерпретатор TUFA
(все скриптовые вызовы), `0x004xxxxx` прочие = прямой код движка.

## Как это работает

1. Прокси-DLL подхватывается игрой (единственный импорт из DINPUT8.dll —
   `DirectInput8Create`) и в `DLL_PROCESS_ATTACH` патчит в памяти **один
   dword**: реализацию натива `ResourceRef.set(I)V` (регистрация
   `0x489340`, оригинал `0x47CF80`).
2. Хук исполняет стоковый пролог (анбоксинг аргумента + lookup ресивера),
   затем: обычные значения → стоковый `ResHandle::Set(value)`; magic
   `0x7AFE0000+percent` (ресивер — меш) → запись в шаблонные материалы
   меша; magic `0x7AFD0000+percent` (ресивер — рендер-тип) → запись в
   живые обёртки типа (связный список +0x44).
3. В обоих случаях: в каждом материале класса 0x33 находятся слоты
   ReflectionIntensity и сырая SCX-копия, percent/100 пишется во все
   слоты (+4..+0x18) и в сырую копию (+4).
4. Никакие D3D-вызовы из хука не делаются: движок сам читает
   пропатченные обёртки своим обычным путём отрисовки.
5. В сейве значение хранится как v5-payload; переживает перезапуск.

## Установка и проверка (v1.11)

1. Бэкап игры и сейвов.
2. Заменить `dinput8.dll` **и** положить обновлённый
   `GlassOpacityTuner.java` из `stable_2_w_debug/` (в v1.11 менялась и
   Java — добавлена вторая magic-полоса). Дать игре перекомпилировать
   классы.
3. Удалить старые `grefl.log` и `grefl_dump.bin`.
4. Запустить игру, зайти в гараж, открыть окно настройки стекла
   (magic уходит уже при открытии), подвигать ползунок Reflection —
   отражение должно меняться БЕЗ сохранения; проверить, что альфа
   других объектов (фары, другие стёкла) больше не портится.
5. Прислать `grefl.log` (+ `grefl_dump.bin`, если появится), даже если
   всё работает — финальная сверка конвейера.

## Диагностика

| Симптом | Причина / что делать |
|---------|----------------------|
| Краш при запуске | v1.11 не меняет ничего до гейта; если воспроизведётся — прислать лог и последние строки перед крашем |
| Альфа других объектов портится при движении ползунка | В v1.11 это невозможно (apply удалён); если видно — стоит старый DLL, замените |
| Отражение меняется только после SAVE | Полоса типа не доходит/не находит слоты: ищите в логе строки `0x7AFD....` и шлите лог + дамп |
| `MAGIC 0x7AFD...` + `no refl entries` | Структура типа не совпала с выводом из дизассемблера — пришлите `grefl_dump.bin`, доразберу за одну итерацию |
| Отражения меняются, но не на всех стёклах | Так и задумано: пишется разделяемый ресурс (все машины с этой деталью/типом) |
